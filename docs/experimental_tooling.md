# Reproducible comparison, calibration and evaluation

These tools prepare future experiments. No physical BlueROV2 dataset is bundled.
Files generated by pytest are explicitly synthetic test fixtures. Command replay
without a native backend has no vehicle dynamics and reports mission completion
as `null`. Executing all command rows is a separate outcome.

## Same command history, L0 and L1

`fidelity_level: L0|L1` is resolved automatically from the existing battery `model`.
Conflicting declarations and L2 fail. L0 is `energy_bucket`, constant voltage,
energy-derived SOC, zero internal loss and fixed reference temperature. L1 is
`rint`, reference Coulomb SOC, OCV(SOC,T), effective R, sag, accessible capacity,
limits and a thermal state. The rest of the loads and the nonlinear manager are
shared. `with_fidelity(config,"L0",capacity_Wh=...)` converts an L1 configuration
without altering commands; absent explicit Wh, its nominal Ah × V baseline is
declared uncalibrated. L1 cannot be invented from an L0 profile.

    python examples/compare_energy_models.py --backend synthetic --steps 300 --output-dir logs/comparison
    <HoloOcean-Python> examples/compare_energy_models.py --backend holoocean --steps 300 --output-dir logs/native_comparison

For a user mission, use a CSV with `time_s,action,sensor_states,water_temperature_C`.
`time_s` is the tick-start time in seconds, beginning at zero at configured dt.
`action` is a JSON array in the configured direct-thruster units; `sensor_states`
is an optional JSON object. Water temperature is optional. No PWM-to-force,
coordinate convention, resampling or time alignment is guessed. Identify these
before converting real histories. Pack temperature remains a model prediction.

    python -m holoenergy.analysis.cli compare --config configs/bluerov2_energy.yaml --mission MY_COMMANDS.csv --output-dir logs/comparison

Each model gets its own log, sidecar and metrics; comparison.csv/json has terminal
Wh, final SOC, V/I/T extrema, load/converter/internal Wh, unmet Wh/peak W, derating
events/duration, cutoff time, command completion and runtime overhead. Complete
V/I/T profiles are in energy.jsonl. Runtime measures step calls including logging;
backend startup is excluded and timing is machine/load dependent. Use repeated
benchmarks before publishing overhead. A supplied seed records a study input;
native sensor/engine RNG seeding requires its own documented backend setup.

The Python API accepts `backend_factory(config)->(reset_env,contract)`, an action
adapter and `completion_observer(state)->bool`. Only an explicit vehicle goal
observer establishes mission completion/time. `power_feasible` and successful
command execution do not establish mission completion. Without a goal criterion,
completion and its time remain null even in native HoloOcean.

## Parameter studies

Run separately from the core simulation:

    python -m holoenergy.analysis.cli sensitivity --config configs/bluerov2_energy.yaml --mission MY_COMMANDS.csv --specification MY_STUDY.json --output-dir logs/study

Specification example (a user-selected illustration, **not BlueROV2 uncertainty**):

```json
{
  "mode": "sensitivity",
  "parameters": {
    "battery.internal_resistance_ohm": {"relative_changes": [-0.2,-0.1,0,0.1,0.2]},
    "thermal.thermal_capacity_J_per_C": {"relative_changes": [-0.1,0.1]},
    "thermal.cooling_coeff_W_per_C": {"values": [1.8,2.2]},
    "hotel_load.constant_W": {"relative_changes": [-0.1,0.1]},
    "sensors.Camera.states.active_W": {"relative_changes": [-0.1,0.1]},
    "converters.payload_efficiency": {"values": [0.85,0.95]},
    "battery.capacity_Ah": {"relative_changes": [-0.1,0.1]}
  }
}
```

One parameter changes at a time; all selected baseline scalar values are recorded.
Nested scalar paths refer to resolved configuration. A supplied R(SOC,T) surface
supersedes `internal_resistance_ohm`; perturb its identified knots externally or
provide distinct calibrated profiles, rather than varying an inactive scalar.
L0 uses capacity_Wh. This is scenario sensitivity, not global sensitivity indices.

Monte Carlo requires `mode: monte_carlo`, an integer `seed`, positive `samples`,
explicit `independent: true` and user-specified parameter distributions. Supported
forms: `{"distribution":"uniform","low":a,"high":b}`,
`{"distribution":"normal","mean":m,"std":s}`, or
`{"distribution":"choice","values":[...]}`. No default intervals/distributions
are supplied. Correlated input sampling and adaptive coverage are not implemented.
Normal distributions can produce invalid physical draws: these remain failed
records, never clipped or resampled. Report their number; a study with failed
draws does not by itself justify an uncertainty interval. study.csv/json preserves
all draws and every successful run's sidecar. Python RNG/runtime versions and
full specification are retained. Use independent measured uncertainty and justify
sample count/convergence before reporting probabilistic conclusions.

## Identified battery-map import

Provide pack-level `temperature_C,soc,ocv_V,resistance_ohm`. OCV and R may be
imported individually by omitting the other entire column. Each included field
needs a complete common SOC grid spanning 0–1 at all supplied temperatures.
Missing cells, duplicate knots and nonmonotone OCV fail. The importer does not
fit raw pulses, average replicates, extrapolate missing knots or replace relaxation
measurements with loaded voltage. Perform identification and uncertainty analysis
on registered calibration runs first. Record rest and pulse duration, hardware
serial, instrument calibration and the **reference-capacity SOC basis**.

Optional separate CSVs: `temperature_C,available_capacity_Ah` and
`temperature_C,max_current_A`. Supply explicit reference Ah/A. Factors are measured
values divided by those references, with capacity factor in (0,1] and current
factor in [0,1]. Reference capacity must be the highest characterized usable
capacity. Current must describe a justified deliverable limit, not observed
mission current. Fitting accessible capacity independently from loaded cutoff
can double-count voltage sag; follow the calibration protocol.

    python -m holoenergy.analysis.cli import-battery MEASURED_MAPS.csv --manifest DATASETS.json --base-config configs/bluerov2_energy.yaml --protocol MY_PROTOCOL --output MY_BATTERY.json

Additional flags: --capacity-csv, --current-csv, --reference-capacity-ah,
--reference-current-a. With --base-config, output is a full battery profile;
otherwise it is an overlay. Preserve other placeholders and characterize thermal,
hotel and electronics separately. Imported fields are labelled user measurements,
not manufacturer coefficients. Superseded R(T) fields are recorded as inactive.
The importer does not establish experimental validation or automatically claim
all temperature effects characterized. Use --base-config with matching reference
capacity/current; a mismatch fails. Use the resulting local battery profile in
the wrapper configuration. Changing a physical reference requires a deliberate
new baseline configuration and SOC convention.

## Dataset separation and hashes

Keep calibration/ and validation/ or equivalent directories outside Git when
appropriate. Register entire independent cycles/missions **before fitting** in a
single versioned manifest. A minimal shape:

```json
{
  "schema_version": 1,
  "dataset_kind": "experimental",
  "runs": [
    {"run_id":"cal_run", "role":"parameter_identification",
     "path":"calibration/run.csv", "sha256":"ACTUAL_SHA256",
     "independence_group":"physical_cycle_1"},
    {"run_id":"selection_run", "role":"model_selection",
     "path":"calibration/selection.csv", "sha256":"ACTUAL_SHA256",
     "independence_group":"physical_cycle_2"},
    {"run_id":"held_out_run", "role":"final_validation",
     "path":"validation/run.csv", "sha256":"ACTUAL_SHA256",
     "independence_group":"physical_cycle_3"}
  ]
}
```

Paths resolve relative to the manifest. Compute actual hashes with file_hash or
Get-FileHash; the strings above are schema placeholders, not working data.
`verify-manifest DATASETS.json` rejects changed bytes, reused IDs/content and
cycle/mission groups crossing roles. Map import requires every CSV hash assigned
to parameter_identification. The evaluator requires a declared run and role;
final_validation is its default. Identification run IDs in prediction profile
metadata must still belong to identification. For separate derived files preserve
raw-parent identity in independence_group and archive the processing script.
Hashes verify declared content/separation, not truthful provenance; researchers
must disclose shared preprocessing, reused physical cycles and human tuning.

## Synchronized real-log evaluation

Canonical columns: numeric `time_s` (or `timestamp`) in seconds, `voltage_V`,
`current_A`, `power_total_W`, `temperature_C`, `water_temperature_C`, `soc`,
`thruster_commands` (JSON), `vehicle_state` (JSON), `sensor_states` (JSON).
State fields are preserved but do not imply an electrical consumption model.
Provide optional mission_completed, completion_time_s, battery_state and
derating_factor for mission/event comparisons. A --columns JSON file maps canonical
names to hardware-log column names. Missing channels yield null metrics, never
invented observations. SOC needs independent reference-based charge accounting.
Separate episodes/reset clocks; times must be strictly increasing.

    python -m holoenergy.analysis.cli evaluate --predicted logs/run/energy.jsonl --measured validation/run.csv --manifest DATASETS.json --run-id held_out_run --output logs/evaluation.json

Metrics include V/I/P MAE/RMSE/max, temperature MAE/RMSE/max and paired peak/time
errors, Wh and relative Wh error, final SOC error, mission completion/time, first
cutoff/derating timing errors and optional reserve violations. Relative Wh error
is null for zero measured energy. Unobserved events/completion remain unknown.
L0 has no thermal prediction, so thermal residual metrics are unavailable.

Default pairing is exact within 1e-8 s. --alignment linear explicitly opts into
piecewise linear interpolation inside prediction coverage, without extrapolation
or fitted lag. Equal-weight sample metrics are not time-weighted under irregular
sampling. Anti-alias and synchronize using instrumentation knowledge; the evaluator
does not optimize a time offset against validation data. Missing pairs are reported
through n counts; inspect coverage instead of interpreting a partial metric as full
mission accuracy. First events use tick/sample resolution; missing events have no
timing-error number.

HoloEnergy logs contain interval-mean electrical values and interval-end SOC/T.
Default predicted-sample-kind is interval_mean; means require dt_s and complete,
nonoverlapping intervals for Wh. Measured default is instantaneous: power is
measured directly or simultaneous V×I, then trapezoid-integrated on original
timestamps over common coverage. For measured interval means explicitly select
--measured-sample-kind interval_mean and supply mean power: mean V × mean I is
**not** mean power. Compare like sampling conventions for point residual metrics.
Energy errors are computed over common coverage and can differ from whole-run Wh.
Gaps/overlaps or missing power leave energy error null with a reason. Archive raw
logs even when a preprocessed time grid is used for residuals.

## Run provenance

Every wrapper run has in-memory logger.metadata, and enabled logs have a sidecar:
UTC time, UUID, package/Python/HoloOcean versions, Git commit and dirty status,
scenario definition/overrides, fully resolved configuration/hash, battery/thruster/
sensor profiles/hashes, input hashes, seed, remaining placeholders and declared
calibration status. Finalization writes output hash and closed/partial status.
Replay also retains full command history/hash, metrics and runtime; retain sidecars
with all outputs. HoloOcean installed-version metadata does not imply that a
synthetic backend used HoloOcean. Absent Git (installed wheel) is explicitly null;
archive release artifacts/version hashes. Dirty runs must archive working files;
prefer a clean experimental commit. Calibration status is a recorded declaration,
not a status inferred from passing software tests.
